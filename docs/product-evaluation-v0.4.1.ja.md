# v0.4.1 の独立評価

評価日：2026-09-12。v0.4.1 相当の作業ツリーをリリースビルドし、実装・実TUI・実測値を対象に評価します。
参加者を伴う調査ではなく、評価者1名による実機評価です。以下の所要時間はすべて1回の実行値で、
中央値でもp95でもありません。1回の測定を一般的なベンチマークとして扱わないでください。

**この文書の読み方（2026-09-12 追記）**：各指摘の本文は、修正前（評価時点の v0.4.1 相当）に
観測した内容をそのまま残しています。同じブランチ `perf/refresh-responsiveness` で解消したものには
**修正済み**と対応コミットを付記し、修正後の実測値は「[修正後の実測](#修正後の実測)」にまとめました。
ソースの引用は、行番号が移動しても追えるようシンボル名に置き換えています。

## ベースラインの健全性

単体238件・統合19件のテストが成功し、`cargo clippy --all-targets` は警告なしでした。
以下の指摘は、この健全な状態の上で観測したものです。

## 優先度1 応答性

### ① タイムアウト待機が固定25msポーリング

`src/git/exec.rs` の `run_with_timeout` が固定25msの `try_wait` ポーリングで待機します。
1回の呼び出しに25.8msを要し、素の `Command::output()` の0.54msと比べて差があります。
6コミットのリポジトリでの `get_summary` は416msで、そのうち実際のGit処理は約11msでした。

13コマンドの一括実行で待機方式を比較しました。

| 待機方式 | 6コミット | 20,000コミット |
|---|---|---|
| 固定25msポーリング（現状） | 333ms | 486ms |
| バックオフ 200µs→25ms | 22ms | 175ms |
| バックオフ 200µs→2ms | 12ms | 148ms |
| ヘルパースレッドでのブロッキング待機 | 8ms | 143ms |

方向性：指数バックオフに変更し、タイムアウト時にプロセスをkillする現在の挙動は維持します。

**修正済み** — `74119a7`。200µs から始めて倍々に伸ばし、最初の100msは2ms、それ以降は25msを上限とする
2段構えのバックオフにしました（`next_poll_interval`）。上限を2段にしたのは、短いコマンドの遅延削減を
保ったまま、60秒のfetchが3万回起床していた問題（`d8f7323`）を避けるためです。

### ② 主要ジョブが単一ワーカーを共有

`LoadHome`、`LoadRepo`、`LoadDiff`、`LoadBlame`、`LoadFiles`、`LoadCommitMeta`、`LoadBranchLog` の各ジョブが
1本のワーカースレッドを共有します。`Job::is_secondary_worker`（`src/app/types.rs`）が
別系統に振り分けるのはWorkspace・pull・fetch・検索・グローバルメンバーのみです。

30リポジトリ登録時の実測では、初回の全体更新に11.8秒かかりました。
`r` を押した直後にリポジトリを開くと、詳細画面の表示までに14.9秒かかりました。
要求が未処理の `LoadHome` すべての後ろに並ぶためです。サンプルは7コミットのリポジトリなので、
実リポジトリではこれより悪化すると考えられます（これは推測であり、測定値ではありません）。

方向性：Home更新用に小さなプールを持ち、対話操作のジョブを別レーンに分けます。

**修正済み** — `474adf7`。4本目のキューを追加し、`available_parallelism` を 2..=8 にクランプした小さな
プールで処理します（git と gh のプロセスを起こすジョブなので無制限にはしません）。`LoadHome` のみを
そこへ回し、対話系ジョブは順序を保つため専用の単一スレッドのままです。
続く `d8f7323` で、プール化によって顕在化した3件（パニックでスレッドが恒久的に失われる、長時間コマンドの
過剰な起床、世代切り替えで取り残される実行中マーカー）も塞いでいます。

### ③ Home行が使わない統計まで毎回取得

`src/git/status.rs` の `get_summary` はHome行1件あたり13コマンドを実行し、
`rev-list --count HEAD`、`ls-tree -r --long HEAD`、`branch -a`、`log -n 50000` を含みます。
`src/app/worker.rs` の `load_home_row` はそれらの結果を使っていません。
20,000コミット・3,000ファイルのリポジトリでは、13コマンド全体が104ms、Home行に必要な部分集合のみが5msでした。

方向性：Home用の軽量クエリを分け、完全な統計は詳細画面でのみ取得します。

**修正済み** — `625ad58`。Home行が読む項目だけを返す `get_home_summary` を追加し、`load_home_row` を
そちらへ向けました。パスが解決できない場合の早期エラーと `ssh://` の扱いは `get_summary` と同じで、
詳細画面が使う `get_summary` 自体は変更していません。実リポジトリに対して両者を突き合わせるテスト
（クリーン時・コンフリクト中）を追加しています。

### ①②③を合わせた見込み

①②③を合わせると、30リポジトリの更新が11.8秒から1秒を十分下回るところまで改善すると見込みます。
これは見込みであり、修正後に再測定して確かめるべき数値です。結果として記載しているものではありません。

**結果** — 見込みどおりでした。実測値は[修正後の実測](#修正後の実測)にあります。

## 優先度2 表示の信用度

### ④ upstream未設定と同期済みが同じ表示

`HomeRow` に `has_upstream` 相当のフィールドがなく、UIは常に `↑{ahead} ↓{behind}` を描画します
（`src/ui.rs` のHomeテーブル構築部）。このため一度もpushしていないブランチが `↑0 ↓0` と表示されます。
`Summary` は `has_upstream` を保持しているため詳細画面は情報を持っていますが、描画は同じです。

**修正済み** — `e16d817`。`HomeRow` が `UpstreamState` を持ち、リモートなし・上流ブランチなしの場合は
`↑? ↓?` と描画し、どちらであるかを選択リポジトリのパネルに文章で表示します。

### ⑤ 消えたパス・非リポジトリの表示

| 状況 | 観測された表示 |
|---|---|
| 登録済みパスが存在しない | 行に `…` が出たままで、読み込み中と区別できない。フッターに帰属先不明の `No such file or directory (os error 2)` のみ |
| 登録済みディレクトリがGitリポジトリでない | 正常なリポジトリとして描画。ブランチ空欄、`↑0 ↓0`、`Dirty 0` |

いずれも実TUIで観測しました。

**修正済み** — `e16d817`。一括問い合わせに `rev-parse --git-dir` を加え、失敗を行そのものが持つように
しました。セルは `⚠ パスなし` / `⚠ Git管理外` / `⚠ 読取不可` を表示し、フッターはリポジトリ名を示し、
パネルは理由の全文と対処を表示し、`n` フィルタでも抽出できます。既存のキャッシュは、新しい項目が
すべて「不明」を既定値として読み込めます。

### ⑥ 最終fetch時刻が分からない

`ahead`／`behind` は最後のfetch時点の情報ですが、最終fetch時刻はどこにも表示されません
（ソース中に `FETCH_HEAD` の参照がありません）。サイドパネルの「ローカル取得」はツールがローカル状態を
読んだ時刻であり、リモートの新しさと誤読され得ます。

方向性：`FETCH_HEAD` の更新時刻を表示します。

**修正済み** — `e16d817`。パネルが「ローカル読取（作業ツリー）」と「リモート取得（↑↓）」を並べて表示し、
後者は `FETCH_HEAD` の更新時刻です。履歴がない場合・未記録・`ssh://` で取得できない場合も区別します。

### ⑦ CI表示がリポジトリ全体の最新1実行

CIインジケーターは `src/git/github.rs` の `gh run list --limit 1` によるリポジトリ全体の最新実行で、
現在のブランチのものではありません。他人の失敗ブランチで ⚠ が立ち、自分の失敗は見落とされ得ます。
マニュアルには正直に記載されていますが、誤解を招く信号は文書化では解消しません。

方向性：`--branch` を付けます。

**修正済み** — `3851f63`。現在のブランチに限定して問い合わせ、detached HEAD は「問い合わせるブランチが
ない」独立した状態（`GithubState::Detached`）として扱います。リポジトリ全体の実行で暗黙に代用することは
ありません。タイムアウトも `GithubState::TimedOut` として失敗と区別します。

### ⑧ Dirty件数がstaged・unstaged・未追跡の合算

Homeの `Dirty` はstaged、unstaged、未追跡を合算した件数です。
追跡対象の変更2件とビルド生成物の未追跡5件があるリポジトリで `7` と表示されるのを観測しました。
Statusタブは `[M]` と `[?]` を区別しているため、情報自体は存在します。

**修正済み** — `e16d817`。追跡対象と未追跡を分けて `2M 5?` のように表示します。内訳を持たない古い
キャッシュ由来の行は、推測せず合計のみを表示します。

## 優先度3 「次に着手する場所」という主張

### ⑨ 要対応の判定範囲が狭い

`src/app/helpers.rs` の `needs_attention` が対象とするのは、コンフリクト、進行中の操作、CI失敗のみです。
`behind > 0`、長期間放置された作業ツリー、upstream未設定は対象外です。
GitHubから取得しているのはオープンPRの件数のみで（`gh pr list --json number`）、
レビュー依頼の有無、draft状態、`reviewDecision`、`statusCheckRollup` は使っていません。
これらは観測専用ツールとして最も行動につながる信号であり、かつ現在実行している `gh` 呼び出しで取得可能な範囲です。

**一部対応・未決着** — `3851f63` で、すでに実行していたPR問い合わせから、現在のブランチのPR（`isDraft`、
`reviewDecision`）と、自分にレビュー依頼が来ているPRの件数を取得・表示するようにしました。要対応の判定には
「自分へのレビュー依頼」と「このブランチのPRへの変更要求」を追加し、いずれもパネルに理由を表示します。
一方で `behind > 0` は**意図的に対象外のまま**です。ほぼすべてのリポジトリが何かに対して遅れているため、
含めると `n` フィルタがほぼ全件を選んでしまいます。下書きPRと承認済みPRも、前者は本人の選択であり、
後者のマージは本ツールが行わない書き込み操作であるため対象外です。長期間放置された作業ツリーと
upstream未設定は引き続き未対応で、この指摘は完全には閉じていません。

### ⑩ 常にCommitsタブから始まる

リポジトリを開くと常にCommitsタブに着地します（`src/app/mod.rs` の `open_repo_state`）。
コンフリクトや未コミット7件を理由に選んだ場合でも同じです。
タブ列は「1 Status」から始まり、READMEもStatusから差分へ進む流れを説明しています。

方向性：作業ツリーが汚れている場合やコンフリクト時はStatusに着地させます。

**修正済み** — `e5f278b`。`landing_tab` が、行またはキャッシュ済みスナップショットに未コミット・
コンフリクト・中断中の操作があればStatusに、なければCommitsに着地させます。判定は開いた時点の1回だけで、
あとから読み込みが完了してもタブは動きません。

### ⑪ 横断コミット検索の条件と上限

横断コミット検索はメッセージの部分一致のみで、著者・パス・日付の絞り込みがありません。
リポジトリごと50件・全体300件の上限（`src/app/worker.rs` の `SEARCH_HITS_PER_REPO` /
`SEARCH_HITS_TOTAL`）に達しても、見出しにその旨が示されません。

**修正済み** — `d3a72c4`。同じ1行のプロンプトで `author:` / `path:` / `since:` / `until:` を解釈し、
それ以外の語はメッセージ本文のままです（`fix(auth):` などがそのまま検索できます）。`author:` は
`members.json` の別名にも広がります。値はすべて `-` 始まりと制御文字を拒否し、`-F` で固定文字列として
扱い、pathspec は必ず `--` で終端します。上限は、上限＋1件を git に要求して超過を検出し、
どちらの上限に当たったか・何リポジトリが該当したかを見出しに表示します。

## 優先度4 委譲（他ツールへの受け渡し）

### ⑫ エディタにリポジトリルートしか渡らない

`src/app/tools.rs` のエディタ起動は `{path}` のみを置換し、`src/app/mod.rs` の `current_work_path` は
常にリポジトリのパスを返します。このため、あるファイルの差分を見ている最中に `O` から `e` を押しても、
そのファイルではなくリポジトリルートが開きます。

方向性：`{file}` / `{line}` / `{branch}` / `{hash}` のプレースホルダーを追加します。

**修正済み** — `e5f278b`。`src/handoff.rs` に `ToolContext` と `expand` を追加し、
`{path}` / `{file}` / `{line}` / `{branch}` / `{hash}` を置換します。その画面で値のない
プレースホルダは、空文字に置換せず起動を中止して欠けている名前を伝えます。置換値は制御文字と
引数の先頭 `-` を拒否し、プレースホルダを実行ファイル名にすることもできません。

### ⑬ ツールメニューが固定

ツールメニューはシェル／エディタ／lazygit／GitUI の固定集合です（`src/app/tools.rs`）。
利用者が独自コマンドを追加することはできません。

**修正済み** — `e5f278b`。設定画面または `O` メニューの `x` から、独自コマンドを6件まで
（`handoff::MAX_CUSTOM_COMMANDS`）追加・編集・削除できます。既定の4つと同じプレースホルダ語彙と
未導入マーカーを共有し、メニューには `1` – `6` として並びます。

### ⑭ yankがない

コミットハッシュ、ブランチ名、パスをクリップボードへコピーする手段がありません。
なお本コードベースはGit出力からOSC 52を意図的に除去しています
（`src/git/exec.rs` の `strip_control_sequences`）。
将来yankを実装する場合は、この方針と混ざらない明示的な別経路にする必要があります。

**修正済み** — `e5f278b`。`y` が選択対象の識別子をコピーします（`src/clipboard.rs`）。除去方針との
区別は出所です。この送信内容は利用者が求め、こちら側で選んだ文字列なので、サニタイズし、長さ上限を設け、
base64化してフレーム間に1回だけ出力します。確認メッセージは「クリップボードに書き込んだ」とは言わず、
端末が無視する可能性があることを伝えます。

### ⑮ 非対話モードがない

`git-dashboard-tui <path>` は不明な引数として拒否されます（`src/main.rs`）。
スクリプト、ステータスライン、エージェントから使えるJSONスナップショット出力もありません。

**修正済み** — `cef6092`。`src/cli.rs` を追加し、`git-dashboard-tui PATH` は `config.json` に
書き込まずそのリポジトリを選択した状態で起動します（`(未登録)` と表示）。`--json` は端末を初期化せず
スナップショットを出力して終了し、ネットワークアクセスを行いません。CI と PR はキャッシュから読み、
値がない・古い場合はその旨を示します。読み取れないリポジトリはゼロではなく失敗として報告し、
upstream がない場合の ahead/behind は `null` です。出力はスキーマ名とバージョンを持つオブジェクトです。
引数解析は `OsString` を受け取り（リポジトリパスがUTF-8とは限らないため）、端末なしでテストできる
モジュールに置いています。終了コードは解釈できないコマンドラインが `2`、設定・パスを読めない場合が `1` です。

- ヘルプ画面は全画面分を1つにまとめた62行のフラットな一覧で、44行の端末では27行しか収まりません。
  **修正済み** — `886ffe5`。`?` を押した画面のセクションを先頭に、続いて全体共通、区切りの下にその他の画面を
  並べます。フラットな一覧に一度も載っていなかった5画面（Worktree一覧、コミット検索、リポジトリ検出、
  ブランチログ、ツールメニュー）と、`docs/reference.md` にしかなかった十数個のキーも追加しました。
- Homeの `Path` 列は長い共通プレフィックスで埋まり、通常の幅では実質的に情報になっていません。
  **修正済み** — `e16d817`。ホーム相対（`~/…`）で中央を省略したパスを表示します。
- 横断Worktree一覧で、パスを参照できない行は `Dirty ?` と表示される一方、ヘッダーは `errors: 0` のままで、説明がありません。
  **修正済み** — `886ffe5`。行の失敗は理由を持ち、`[` / `]` の一覧に加わり、ヘッダーでは正常な件数ではなく
  `unknown` として数えます。

  ②が解消するまでは再試行のたびに共有ワーカー1本を占有します。
  **修正済み** — `3851f63`。上限を10秒にし、再試行を原因別に段階化しました（通常の失敗60秒、タイムアウト180秒、
  gh未導入・未認証は更新周期と同じ300秒）。②の解消により、再試行が対話操作のレーンを占有することもありません。

- 観測専用という位置付けが一貫して守られています。書き込み操作は限定的で、かつ文書化されています。
- 開発上の衛生状態が良好です。単体238件・統合19件のテスト、Clippy警告なし、MSRVの固定とCIでの確認、
  設定ファイルのアトミック書き込み、チェックサムを検証するインストーラー、出力サイズの上限、
  制御シーケンスの除去、SSH問い合わせのバッチ化、起動時に内容が表示されるディスクキャッシュ、中止可能なフォルダ走査。
- 差分ビューアは実際に高速です。60,000行のファイル中8,572行が変更された差分を開き、
  ハンクジャンプとblame表示の切り替えを行っても、体感できる遅延はありませんでした。

## 修正後の実測

修正後の値は、同じサンドボックス・同じフィクスチャで、実バイナリをPTY上で駆動して修正前後を連続して
測定したものです。修正前の値も同じ手順で取り直しているため、本文中のベースライン（11.8秒・14.9秒など）
とは僅かに異なります。いずれも1回の測定値で、中央値でもp95でもありません。

| 測定 | 修正前 | 修正後 |
|---|---|---|
| 30リポジトリのコールドな全体更新 | 13.83秒 | 0.23秒 |
| `r` を押した直後にリポジトリを開く（詳細画面の表示まで） | 14.49秒 | 0.17秒 |
| 20,000コミットのリポジトリを含む10リポジトリの更新 | 4.96秒 | 0.21秒 |

**この数値が成り立つ条件**：フィクスチャのリポジトリにはGitHubリモートがありません。したがってこれらは
**ローカルのGit処理のみ**を測ったものです。GitHubリモートを持つリポジトリのコールドな更新は、
依然として `gh` の呼び出し時間に律速されます（1回あたり上限10秒、リポジトリあたり3回の逐次呼び出し）。
ネットワークファイルシステムや低速ディスクでの測定も引き続き行っていません。
