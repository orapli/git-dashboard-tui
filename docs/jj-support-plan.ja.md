# Jujutsu (jj) 対応プラン

提案段階の計画であり、未着手です。検証日：2026-09-12。
検証環境：Linux aarch64、jj 0.45.1、git 2.53.0。本文の「確認済み」は、この環境で
実際にコマンドを実行して得た結果です。他OS・他バージョンでは未検証です。

対象は **git と併存する colocated リポジトリ**（`jj git init --colocate`）を第一とします。
理由は第6節に書きます。

## 1. 動機：現状はjj利用者に誤った状態を表示する

jjの通常のワークフロー（`jj new` で無名の変更の上に作業する）に入ると、git側のHEADは
detachedになります。このツールはgitのみを見ているため、作業中のリポジトリが
「ブランチなし・変更なし・同期済み」に見えます。

| 観測 | `jj git init --colocate` 直後 | `jj new` 後（通常の作業状態） |
|---|---|---|
| `git branch --show-current` | `main` | 空 |
| `git rev-parse --abbrev-ref HEAD` | `main` | `HEAD`（detached） |
| `git status --porcelain` | 空 | 空 |
| `git rev-parse --abbrev-ref @{u}` | 失敗（upstream未設定） | 失敗 |

このときjj側には説明のない変更が2件積まれていました。Home行の表示は
Branch列が空、Sync列が `↑0 ↓0`、Dirty が 0 になります。
`↑0 ↓0` が「upstreamなし」と区別できない件は
[v0.4.1の評価](product-evaluation-v0.4.1.ja.md)の指摘④と同じ問題で、jjでは常時これを踏みます。

一方で**Dirty列は壊れていません**。colocatedリポジトリではjjが作業コピーの内容をgitの
インデックスに反映するため、`@` の変更は `git status --porcelain` に出ます。
コンフリクトも `AA` として出るので、既存の `count_conflicts` は `@` のコンフリクトを拾えます
（ただし `MERGE_HEAD` は存在しないため ⚠MERGE は出ず、`@` 以外の変更が抱えたままの
コンフリクトはgitからは見えません）。

## 2. 検証で確定した事実

| 項目 | 結果 | 確認方法 |
|---|---|---|
| 素の `jj log` は書き込む | オペレーションIDが変化（作業コピーのスナップショットが記録される） | `jj op log --limit 1` の前後比較 |
| `--ignore-working-copy` は読み取り専用 | オペレーションIDが不変 | 同上 |
| jjの起動コスト | `log -r @` 5ms、`bookmark list` 4ms（参考：`git status` 1ms） | 各コマンドの実測 |
| 差分はgit形式 | `jj diff --git` が標準の unified diff を出力 | 出力を目視確認 |
| テンプレートで機械可読出力が得られる | `-T 'change_id.short() ++ ...'` が期待通り | 実行確認 |
| revsetが使える | `conflicts()` / `divergent()` が解決される | 実行確認 |
| ブックマークの一覧が取れる | `bookmark list --all-remotes` がローカルと `@git` を出力 | 実行確認 |
| リポジトリ検出 | `scan_repositories` は `.git` の存在で判定（`src/app/finder.rs:166`） | ソース確認 |

## 3. 設計方針

**方針1：jj呼び出しには必ず `--ignore-working-copy` を付ける。**
このツールは観測専用です。素の `jj` コマンドは作業コピーをスナップショットしてオペレーション
ログに書き込むため、そのままでは方針に反します。利用者自身のjjコマンドとロックを
奪い合わないという利点もあります。代償として `@` の内容は「最後のスナップショット時点」に
なりますが、これは本アプリが既に持つ「取得時刻／古いキャッシュ」の表現で扱えます。

**方針2：jj情報が取れないときはgit表示に無害に縮退する。**
jjが未導入、バージョン不一致、出力のパース失敗、いずれの場合も「jj情報なし」に落として、
既存のgitベースの表示は決して壊しません。ツールメニューの `[未導入・PATHなし]` と同じ流儀です。

**方針3：バージョン差異に備える。**
jjは1.0前でCLIが変化します（`branch` → `bookmark` の改名が実例）。出力は必ず `-T`
テンプレートで明示的に指定し、`jj --version` で対応範囲を判定し、対応範囲をマニュアルに明記します。

## 4. フェーズ1：誤表示を止める（小・優先）

第1節の誤表示だけを解消します。タブもパネルも追加しません。

* **検出**：リポジトリ直下に `.jj` ディレクトリが存在するか。ファイルシステムの確認のみで、
  プロセス起動は不要です。
* **Branch列**：jjリポジトリでは、gitの空文字の代わりに `@` が指すブックマーク
  （無ければ change ID の短縮形）を表示します。取得は
  `jj --ignore-working-copy log -r @ --no-graph -T '...'` の1回。
* **行バッジ**：既存の `⚠MERGE` と同じ位置に `jj` を表示し、gitだけでは説明できない状態で
  あることを示します。
* **ツールメニュー**：`.jj` があるとき `O` に `jj` と `lazyjj` を追加します。

触るファイル：`src/git/`（新規 `jj.rs`）、`src/app/types.rs`（`HomeRow`）、
`src/app/worker.rs`（`load_home_row`）、`src/ui.rs`（Home表）。

受け入れ条件：colocatedリポジトリで `jj new` 後もBranch列が空にならないこと。
jj未導入の環境で表示・性能ともに現状から変化しないこと。Home更新1回あたりのjj呼び出しが
1リポジトリ1回を超えないこと。

## 5. フェーズ2：条件付きタブ「8 jj」

`.jj` があるリポジトリでのみ表示されるタブを追加します。

| セクション | 取得（すべて `--ignore-working-copy`） |
|---|---|
| `@` の状態 | `log -r @ --no-graph -T '...'` — change ID / 説明の有無 / empty / conflict |
| 作業コピーの変更 | `diff --summary -r @` → 選択して既存の差分ビューアへ |
| 変更スタック | `log -r 'ancestors(@, N)' --no-graph -T '...'` |
| ブックマーク | `bookmark list --all-remotes` — リモートとのずれ、conflicted bookmark |
| オペレーションログ | `op log --limit 20 --no-graph -T '...'` |

差分は `jj diff --git` が標準のgit形式を出すため、**既存のパーサとビューアをそのまま再利用**
できます。ここが実装コストを大きく下げる要点です。
オペレーションログはjj固有で、「直前に何をしたか／何をundoできるか」を見せるだけの
純粋な参照機能であり、本ツールの位置づけと最も相性が良い項目です。

触るファイル：`src/git/jj.rs`、`src/app/types.rs`（`RepoTab` / スナップショット）、
`src/app/worker.rs`、`src/ui.rs`（詳細画面）、`src/app/mod.rs`（タブ遷移）、`docs/reference.md` 系。

受け入れ条件：タブはjjリポジトリでのみ現れ、キー番号の割り当てが既存の1〜7と衝突しないこと。
jjコマンドが失敗してもタブ内にエラーを表示するだけで、他タブが壊れないこと。

## 6. フェーズ3：jj固有のattention信号

jjのコンフリクトはコミットに永続するため、gitの一時的なMERGE状態より
「次に着手する場所」の信号として質が高くなります。

* コンフリクトを含む変更：`log -r 'conflicts()'` の件数
* 分岐した変更：`log -r 'divergent()'` の件数
* conflicted bookmark：`bookmark list` の状態

これらを `needs_attention` に加え、選択リポジトリのパネルに理由として文章で出します。
`@` に説明が無いことを警告に含めるかは意見が割れるため、既定では入れません。

## 7. 判断が必要な点：非colocatedリポジトリ

`jj git init` を `--colocate` なしで作ったリポジトリは直下に `.git` を持たないため、
リポジトリ検出（`src/app/finder.rs:166`）に引っかからず、そもそも登録できません。
選択肢は2つです。

1. `.jj` も検出マーカーに加える。ただしgit系の表示（ブランチ、ahead/behind、
   `git status`）はすべて成立しないため、jj情報だけで行を構成する必要があり、
   実質「gitダッシュボードにjj専用の行種別を足す」ことになります。
2. 当面は非対応と明記し、colocatedのみを対象とする。

フェーズ1〜3は選択肢2を前提にしています。1に進むかは、フェーズ2の実装後に
実利用の要望を見てから判断するのが妥当です。

## 8. リスクと未検証事項

* jjのCLI変化。対応範囲を明記し、パース失敗時はgit表示に縮退する（方針2・3）。
* 本プランはjj 0.45.1・Linux aarch64 の1環境でしか確認していません。macOS・Windowsでの
  挙動、特にパス処理とプロセス起動コストは未検証です。
* `ssh://` 登録のリポジトリは対象外です（ローカルのjj実行ができないため、現在の
  ローカルツール制限と同じ扱いになります）。
* 計測は単発です。リポジトリ数が多い構成でのjj呼び出しの合計コストは、
  Home更新の並列化（[評価](product-evaluation-v0.4.1.ja.md)の②）が入った後に再測定が必要です。

## 9. 対象外

jj側の書き込み操作（`describe` / `new` / `squash` / `abandon` など）は追加しません。
本ツールは観測専用という方針であり、実作業は既存のツールへ委譲します。
jjに対する「委譲」は、フェーズ1のツールメニュー（`jj` / `lazyjj` の起動）で完結させます。
