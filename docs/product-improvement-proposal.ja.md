# git-dashboard-tui 商品魅力向上の改善案

作成日: 2026-09-05 / 確認対象: v0.3.1、コミット `b93db27`

## 提案の中心

**「複数リポジトリの状態を見て、次に着手する場所をすぐ決められる」体験を磨く。**

対象ユーザーは、日常的に複数のリポジトリを行き来する開発者・テックリードと仮定する。まずは「仕事を始めるとき」「別の案件へ戻るとき」に開きたくなる道具を目指す。

一覧、要対応フィルタ、横断コミット検索、グループ、Worktree 表示、シェルへの移動は実装済み。この土台を使い、価値の伝わり方、初回体験、判断のしやすさ、作業への接続を改善する。

以下はソースとドキュメントの確認に基づく提案。実機の操作評価、利用者インタビュー、需要・支払意思の検証は未実施。優先度は仮説であり、工数は相対評価とする。

| 確認できたこと | 改善の機会 | 根拠 |
|---|---|---|

| 初回の空画面の本文は `a` による単体登録を案内する | 複数管理が売りなので、一括登録 `A` を主導線にする | [draw_home](../src/ui.rs) |

## 優先順位

効果は期待する変化であり、実測済みの改善率ではない。

| 順位 | 改善案 | ユーザーにとっての魅力 | 相対工数 |
|---|---|---|---|
| 1 | 紹介文と短い体験デモを刷新 | 自分が使う理由をすぐ理解できる | 小 |
| 2 | 初回の一括登録と体験ガイド | インストール直後から複数管理の便利さが分かる | 小〜中 |
| 3 | Home に要対応サマリーと理由を表示 | 次に見るべきリポジトリを迷わず選べる | 中 |
| 4 | 鮮度・CI 対象・取得状態を明示 | 表示を根拠に安心して判断できる | 中 |
| 5 | エディタ・Git クライアントへの直接移動 | 状態確認から作業までの手間が減る | 中 |
| 6 | リポジトリを横断する Worktree 一覧 | 並行作業を把握し、途中の仕事に戻りやすい | 中〜大 |

### 1. 紹介文と短い体験デモを刷新する

**コピー案**

> 散らばったリポジトリから、次に取りかかる場所が見える。
>
> 未コミットの変更、同期状態、CI の失敗をひとつの画面で確認。
> 気になるリポジトリの差分を見て、その場からシェルへ移動できます。

README 冒頭を「コピー → 具体的な利用シーン → 短いデモ → インストール」の順に整える。デモは「フォルダを一括登録 → `n` で要対応を絞る → 差分を確認 → `t` で作業へ」の一連の流れを約 30 秒で見せる。

既存の合成リポジトリ生成・実画面キャプチャを活用する。架空の CI 状態を使う場合はサンプル表示と分かるようにする。すでにある機能を使うため、機能開発を待たずに着手できる。

同時に「読み取り専用」を「状態確認を中心にしたマルチリポジトリ Git ダッシュボード」へ改め、明示的な操作で pull・fetch・stash 適用・削除ができることを短く説明する。「履歴を書き換えない」という断定も、設定に応じて動く `git pull` と整合する表現へ見直す。

**完了条件:** 日英 README と CLI ヘルプの説明が整合する。初見の協力者が冒頭を見て「誰向けか」「何が楽になるか」を説明できる。マニュアルを変える場合は生成元を編集して再生成する。

### 2. 初回の一括登録と体験ガイド

空画面で「`A` 作業フォルダからまとめて追加」を主導線にし、「`a` 1 件だけ追加」を併記する。既存 Finder を利用し、走査先の入力、検出一覧、登録の順で進める。走査はユーザーの操作で開始する。

登録直後には短い案内を出す。「`n` 要対応だけ見る」「`Enter` 詳細」「`t` 作業へ」「`?` ヘルプ」の 4 操作に絞り、閉じた後は毎回表示しない。

次の段階で `--demo` を検討する。実装するなら通常設定から分離したサンプルを使い、終了後に普段の登録一覧へ混ざらない構成にする。既存の `docs/gen_demo.py` は素材として活用できるが、ユーザー向け起動・終了処理は新規に必要。

**完了条件:** 初見の協力者が口頭説明なしで 3 リポジトリを登録し、そのうち 1 件の差分を開ける。デモ機能は初回改善の必須条件にしない。

### 3. Home に「要対応の理由」と次の操作を出す

既存 `n` フィルタを活かし、Home 上部に要対応リポジトリ数、未コミットあり、同期差分ありを集約する。要対応数はリポジトリ単位で重複を除く。未コミットや behind は通常の作業状態なので、要対応とは別に数える。

選択行の詳細欄に「CI 失敗」「未解決コンフリクト 2 件」「rebase 中」などの理由と関連操作を表示する。集計対象は現在のグループ・検索条件に合わせる。取得できていない件数も併記し、未取得を正常に数えない。

CI の実行ページを開く導線も追加する。その前に案 4 の対象表示を整え、Home に実行 URL と対象の情報を渡せるようにする。狭い端末では詳細を折りたたみ、一覧の読みやすさを優先する。

**完了条件:** 10 リポジトリのサンプルから、利用者が要対応の 1 件とその理由を答え、関連する差分・シェル・CI ページへ移れる。

### 4. 「いつ・何を確認した情報か」を分かるようにする

Home の「更新」を「最終コミット」に改め、情報取得時刻を別に表示する。ローカル状態の再取得とリモートの fetch は別なので、「再読み込みを押せばリモートまで最新になる」と誤認させない。

CI はまず現行動作に合わせて「リポジトリ全体の最新実行」であることとブランチを表示する。現在ブランチに限定するモードや複数 workflow の集約は、追加の仕様として扱う。取得できない場合は正常・実行なし・未認証・失敗・古いキャッシュを区別する。

PR は 100 件取得した場合に `100+` と表示するか、ページングを実装する。どちらにするかは、正確な総数が必要かを利用者に確認して決める。

ローカル情報と GitHub 情報の更新間隔を分け、GitHub 側にはキャッシュと失敗時の待機を入れる。現在の自動更新は初期値オフであり、一律に短周期へ変えることを前提にしない。

**完了条件:** 古い情報・未認証・取得失敗・実行なしをそれぞれ再現して識別できる。別ブランチの CI を現在ブランチの結果と誤認しない。ローカル更新だけでは GitHub 呼び出しを繰り返さない。

### 5. 普段の作業ツールへ直接移動する

選択リポジトリの「開く」メニューに、シェル、設定済みエディタ、lazygit／GitUI を用意する。既存ショートカットと競合しない割り当てを選び、メニュー内にキーを表示する。外部ツールが未導入なら、その状態と設定方法を示す。

端末内で動くツールの終了後は、選択していたリポジトリへ戻って状態を再取得する。GUI エディタは起動方式に応じて扱いを分ける。SSH リポジトリはローカルと同じ起動を約束せず、対応範囲を表示する。

既存のシェル・外部 diff 起動の仕組みを再利用し、コマンド設定を共通化できるか確認する。

**完了条件:** 選択したパスでツールが起動し、端末内ツールの終了後に表示と入力が復帰する。空白を含むパス、未導入ツールでも状況が分かる。

### 6. Worktree を横断して途中の仕事に戻れるようにする

現状は各リポジトリ内で Worktree のパス・ブランチ・HEAD・lock/prunable を確認できる。これを横断一覧へ広げ、親リポジトリ、Worktree、ブランチ、未コミット数、最終コミットをまとめる。任意の用途メモとお気に入りを追加し、「昨日の調査」「レビュー用」など本人の言葉で探せるようにする。

最初はローカル Worktree を対象に、案 5 の作業ツール起動へ接続する。状態取得はバックグラウンドで並列数を制限し、同一 Worktree が親経由と個別登録で二重に並ばないようにする。

AI を使った並行開発も利用場面の仮説に含める。ただし Git 情報だけでエージェントの稼働・完了は判定できないため、表示するのは確認できた Git 状態と利用者のメモに限る。

**完了条件:** 複数リポジトリの Worktree を 1 画面で探し、指定した Worktree 内で作業を始められる。情報取得中も一覧を操作できる。

## 着手するまとまり

最初は案 1・2 と、案 4 の「最終コミット」への名称変更をまとめる。紹介と初回体験を短い開発単位で揃えられる。BACKLOG の実装済み項目も、この段階でソースに照合して整理する。

次に案 3・4 の状態モデルを一緒に設計し、理由・鮮度・対象が一貫して伝わる Home を作る。その後に案 5 をつなぐ。案 6 は Worktree を日常利用する協力者の評価を受けて着手する。

## 効果の確かめ方

初回は対象に近い協力者 5 人程度に、現行版と改善版で同じ課題を依頼する。先に触る版を分け、学習による影響を抑える。小規模な定性検証なので、統計的な効果とは扱わない。

| 検証したい価値 | 観察すること | 仮の合格目安 |
|---|---|---|
| 紹介だけで使う理由が伝わる | 冒頭を見た後の説明 | 5 人中 4 人が複数管理という用途を説明できる |
| 初回から便利さを体験できる | 起動から 3 件登録・差分表示まで | 5 人中 4 人が口頭補助なしで完了 |
| 次に見る場所を選べる | サンプルから要対応と理由を特定する時間 | 現行版より短縮し、誤認が増えない |
| 普段の作業につながる | 対象リポジトリでツールを開いて戻る操作 | パス間違い・端末復帰の失敗がない |
| 習慣になる | 1 週間後の任意ヒアリング | 実際に使った場面と、使わなかった理由を収集 |

数値は目標案で、現時点の実績ではない。計測は協力者の同意のある操作観察・ヒアリングで始め、自動テレメトリ追加を前提にしない。

## 今回の優先範囲

テーマや装飾の追加は、情報の優先順位と初回導線を整えた後に判断する。コミット・rebase などの操作追加、コミット数による人物ランキング、生成 AI による要約は、今回の中心課題への効果を確認してから検討する。

価格や有料プランは利用継続の理由と支払意思を確認した後に設計する。今回の提案は、まず既存プロダクトが選ばれ、継続して使われる魅力を高めることを対象とする。

## 外部情報との照合
