# v0.4.0 初見ユーザー評価の実施票

これは実施手順と記録用紙です。参加者による評価はまだ実施していません。
実装者の操作成功や自動テストを、初見ユーザーの成功として扱わないでください。

## 対象と準備

日常的に複数リポジトリを扱う開発者5名程度を対象にします。参加と記録の同意を得て、
必要に応じて画面共有で観察します。自動送信・テレメトリは追加しません。

同じOS・端末サイズ・サンプルで、普段の方法と本製品を比較します。
半数は普段の方法から、残りは本製品から始め、順序による学習の影響を抑えます。
少人数の結果は定性評価であり、市場全体への統計的な結論にはしません。

合成リポジトリの準備は[ドキュメント生成手順](README.md)の `gen_demo.py` を利用できます。
実際のユーザー設定と混ざらないよう、参加者ごとに新しい設定先を使います。

```bash
GIT_DASHBOARD_CONFIG_DIR=/tmp/gdt-study-participant-01 git-dashboard-tui
```

サンプルは評価者が事前に確認し、少なくともクリーンなリポジトリ、未追跡ファイルがあるもの、
コンフリクトがあるもの、2つのWorktreeを用意します。READMEを読むことは許可し、
下の課題では具体的な操作キーを口頭で教えません。

## 課題カード

1. 作業フォルダから3リポジトリを登録し、未コミットの変更があるものを見つけてください。
2. 新しく作った、まだGitで追跡していないファイルの内容を確認してください。
3. 要対応のリポジトリを見つけ、そう判断した根拠を説明してください。
4. 指定したWorktreeに「明日のレビュー」とメモを残し、その中でシェルを開いてください。
   シェルの `pwd` と指定されたパスが一致するかを評価者が確認します。
5. シェルでサンプルファイルを変更して戻り、変更が反映されたことを確認してください。
6. フォルダ走査を開始して、中止してください。
7. 「未確認」は正常という意味か、再読込はfetchと同じかを、画面と資料から説明してください。

GitHub連携も評価する場合は、参加者の実リポジトリを変更せずに再現できるテスト環境で、
別ブランチのCI結果と古い情報を提示し、作業中ブランチの状態と区別できるかを追加確認します。

## 判定の目安（実績ではなく、検証前の目標）

- 5人中4人以上が、登録からファイル確認まで口頭補助なしで完了する。
- 指定した作業パスの取り違えがない。
- 未確認を正常と誤認しない。
- 普段の方法と比較して状況把握が速くなり、操作ミスが増えない。
- 1週間後、実際に再利用した場面と、使わなかった理由を本人から聞く。

満たさない項目は機能追加で埋める前に、表示・用語・初回導線を見直します。
支払意思、継続率、競合優位はこの小規模テストだけでは実証できません。
